# Requirements Document — Ranking Backend API

## Introduction

This document defines the backend requirements for the **Ranking** product — a web application that allows users to create comparative rankings, add items, and rate them across custom attributes.

### Scope

This SRS covers the **backend REST API** exclusively, implemented in Go 1.25 with Gin-Gonic, deployed on AWS Lambda behind API Gateway, using DynamoDB (single-table design) and S3 for persistence.

### Technical Context

- **Runtime:** AWS Lambda (ARM64, 128 MB) + API Gateway
- **Language:** Go 1.25, Gin-Gonic framework
- **Database:** Amazon DynamoDB (single table, on-demand billing)
- **Object Storage:** Amazon S3 (private, pre-signed URLs)
- **Auth Model:** No authentication — browser UUID v7 via `X-User-Id` header
- **API Style:** RESTful, JSON, versioned (`/api/v1/`), Swagger/OpenAPI documented
- **Architecture:** Clean Architecture + DDD

### Conventions

- All requirements use **User Stories** and **BDD-style Acceptance Criteria** (GIVEN / WHEN / THEN).
- Requirements are numbered as `REQ-XX`.
- Assumptions are referenced as `A-XX` (see `assumptions.md`).
- Each requirement traces to one or more assumptions.

## Glossary

| Term | Definition |
|---|---|
| **Ranking** | A user-created structure that organizes items to be evaluated against custom attributes. |
| **Attribute** | A criterion defined by the ranking creator used to evaluate items (e.g., "Graphics", "Price"). Max 6 per ranking. |
| **Item** | An element within a ranking that users evaluate (e.g., "Sega Mega Drive"). |
| **Rating** | A set of integer scores (0–100) given by a single user to a single item, one score per attribute. |
| **Overall** | The arithmetic mean of all attribute scores for an item. Calculated at read time, never stored. |
| **User ID** | A UUID v7 generated in the browser and sent via `X-User-Id` header. Not an account — a browser-scoped identity. |
| **Visibility** | A ranking property: `public` (discoverable, searchable) or `private` (accessible only via direct URL). |
| **Tag** | An optional keyword attached to a ranking to facilitate search and discovery. |
| **Pre-signed URL** | A time-limited S3 URL generated by the backend to allow the frontend to display private images. |
| **Cursor** | An opaque token used for pagination, derived from DynamoDB's `LastEvaluatedKey`. |
| **Single Table Design** | A DynamoDB modeling pattern where all entities share one table, differentiated by composite keys. |

## Requirements

### REQ-01: Create Ranking

**User Story:**
As a user, I want to create a new ranking with a name, optional description, visibility, optional tags, and attributes, so that I can organize items for evaluation.

**Traces:** A3, A4, A12, A13, A14, A25, A28, A30, A45, A46

#### Acceptance Criteria

1. GIVEN a valid `X-User-Id` header and a request body with `name` (required, 1–100 chars), `description` (optional, max 500 chars), `visibility` (`public` or `private`), `tags` (optional, array, max 10 items), and `attributes` (required, 1–6 items each with `name` 1–50 chars and optional `description` max 200 chars), WHEN the user sends `POST /api/v1/rankings`, THEN the backend creates the ranking, assigns a UUID v7 as the ID, sets `ownerUserId` to the caller's user ID, and returns `201 Created` with the full ranking object.

2. WHEN `name` is missing or empty, THEN the backend returns `400 Bad Request` with error code `VALIDATION_ERROR`.

3. WHEN `attributes` is empty or contains more than 6 items, THEN the backend returns `400 Bad Request` with error code `VALIDATION_ERROR`.

4. WHEN `tags` contains more than 10 items, THEN the backend returns `400 Bad Request` with error code `VALIDATION_ERROR`.

5. WHEN `visibility` is not `public` or `private`, THEN the backend returns `400 Bad Request` with error code `VALIDATION_ERROR`.

6. WHEN `X-User-Id` header is missing or not a valid UUID, THEN the backend returns `400 Bad Request` with error code `MISSING_USER_ID`.

### REQ-02: Get Ranking by ID

**User Story:**
As a user, I want to retrieve a ranking by its ID, so that I can view its details, items, and scores.

**Traces:** A4, A13, A14, A45, A46, A47

#### Acceptance Criteria

1. GIVEN a valid ranking ID, WHEN the user sends `GET /api/v1/rankings/{id}`, THEN the backend returns `200 OK` with the ranking metadata (name, description, visibility, tags, attributes, ownerUserId, createdAt, updatedAt).

2. WHEN the ranking ID does not exist, THEN the backend returns `404 Not Found` with error code `RANKING_NOT_FOUND`.

3. WHEN the ranking is private, THEN the backend still returns it (access is granted by knowing the UUID). No visibility restriction on direct access.

4. WHEN `X-User-Id` header is provided, THEN the response includes an `isOwner` boolean field indicating whether the caller is the ranking creator.

### REQ-03: Update Ranking

**User Story:**
As the ranking creator, I want to update my ranking's name, description, tags, visibility, and attributes, so that I can refine it over time.

**Traces:** A3, A12, A25, A26, A28, A29, A30, A46

#### Acceptance Criteria

1. GIVEN a valid `X-User-Id` matching the ranking's `ownerUserId`, WHEN the user sends `PUT /api/v1/rankings/{id}` with updated fields, THEN the backend updates the ranking and returns `200 OK` with the updated ranking object.

2. WHEN `X-User-Id` does not match the ranking's `ownerUserId`, THEN the backend returns `403 Forbidden` with error code `NOT_OWNER`.

3. WHEN attributes are removed and ratings exist for those attributes, THEN the existing ratings for removed attributes are soft-deleted (excluded from calculations but retained in the database).

4. WHEN the updated attributes list exceeds 6 items, THEN the backend returns `400 Bad Request` with error code `VALIDATION_ERROR`.

5. WHEN the ranking ID does not exist, THEN the backend returns `404 Not Found` with error code `RANKING_NOT_FOUND`.

6. WHEN `X-User-Id` is missing, THEN the backend returns `400 Bad Request` with error code `MISSING_USER_ID`.

### REQ-04: Delete Ranking

**User Story:**
As the ranking creator, I want to delete my ranking, so that I can remove content I no longer want.

**Traces:** A3, A27, A46

#### Acceptance Criteria

1. GIVEN a valid `X-User-Id` matching the ranking's `ownerUserId`, WHEN the user sends `DELETE /api/v1/rankings/{id}`, THEN the backend deletes the ranking and all associated items, ratings, and S3 images, and returns `204 No Content`.

2. WHEN `X-User-Id` does not match the ranking's `ownerUserId`, THEN the backend returns `403 Forbidden` with error code `NOT_OWNER`.

3. WHEN the ranking ID does not exist, THEN the backend returns `404 Not Found` with error code `RANKING_NOT_FOUND`.

4. WHEN `X-User-Id` is missing, THEN the backend returns `400 Bad Request` with error code `MISSING_USER_ID`.

### REQ-05: List Public Rankings

**User Story:**
As a user, I want to browse public rankings with pagination and sorting, so that I can discover interesting rankings.

**Traces:** A4, A13, A15, A43, A44, A45, A49

#### Acceptance Criteria

1. GIVEN no filters, WHEN the user sends `GET /api/v1/rankings`, THEN the backend returns a paginated list of public rankings only, sorted by `createdAt` descending by default.

2. WHEN the `sort` query parameter is provided (e.g., `sort=-createdAt`, `sort=name`), THEN the backend sorts results accordingly following JSON:API convention.

3. WHEN `sort` references an unsupported field, THEN the backend returns `400 Bad Request` with error code `INVALID_SORT_FIELD`.

4. WHEN `limit` query parameter is provided (1–50), THEN the backend returns at most that many results. Default is 20.

5. WHEN `cursor` query parameter is provided, THEN the backend returns results starting after that cursor position.

6. THEN the response includes `data` (array of rankings) and `pagination` object with `nextCursor` (null if no more results) and `hasMore` (boolean).

7. THEN private rankings are never included in this listing.

### REQ-06: Get Recent Public Rankings

**User Story:**
As a user, I want to see the 10 most recently created public rankings, so that I can discover fresh content on the home page.

**Traces:** A13, A20, A41, A45

#### Acceptance Criteria

1. WHEN the user sends `GET /api/v1/rankings/recent`, THEN the backend returns the 10 most recently created public rankings, sorted by `createdAt` descending.

2. THEN the response contains a `data` array with at most 10 ranking summary objects (id, name, description, tags, createdAt).

3. THEN private rankings are never included.

4. WHEN there are fewer than 10 public rankings, THEN the backend returns all available public rankings.

### REQ-07: Search Rankings

**User Story:**
As a user, I want to search rankings by name or tags, so that I can find rankings relevant to my interests.

**Traces:** A4, A13, A40, A42, A43, A44, A45

#### Acceptance Criteria

1. WHEN the user sends `GET /api/v1/rankings/search?q={term}`, THEN the backend returns public rankings whose name contains the search term (partial match, case-insensitive, accent-insensitive).

2. WHEN the user sends `GET /api/v1/rankings/search?tag={tag}`, THEN the backend returns public rankings that have an exact match for the given tag.

3. WHEN both `q` and `tag` are provided, THEN the backend applies both filters (AND logic).

4. WHEN neither `q` nor `tag` is provided, THEN the backend returns `400 Bad Request` with error code `VALIDATION_ERROR`.

5. THEN results are paginated using cursor-based pagination (default 20, max 50).

6. THEN private rankings are never included in search results.

### REQ-08: List My Rankings

**User Story:**
As a user, I want to see all rankings I created, so that I can manage and access them quickly.

**Traces:** A3, A4, A43, A44, A45, A46

#### Acceptance Criteria

1. GIVEN a valid `X-User-Id` header, WHEN the user sends `GET /api/v1/rankings/mine`, THEN the backend returns all rankings (public and private) where `ownerUserId` matches the caller's user ID.

2. THEN results are paginated using cursor-based pagination (default 20, max 50).

3. THEN results are sorted by `createdAt` descending by default, with optional `sort` parameter.

4. WHEN `X-User-Id` is missing, THEN the backend returns `400 Bad Request` with error code `MISSING_USER_ID`.

### REQ-09: Add Item to Ranking

**User Story:**
As a user, I want to add an item to a ranking, so that it can be evaluated by all users.

**Traces:** A4, A14, A32, A33, A46, A51, A52

#### Acceptance Criteria

1. GIVEN a valid `X-User-Id` header and a valid ranking ID, WHEN the user sends `POST /api/v1/rankings/{rankingId}/items` with `name` (required, 1–100 chars) and optional image (file upload or `imageUrl` field), THEN the backend creates the item, assigns a UUID v7, sets `createdBy` to the caller's user ID, and returns `201 Created` with the item object.

2. WHEN the ranking already has 100 items, THEN the backend returns `400 Bad Request` with error code `MAX_ITEMS_REACHED`.

3. WHEN the ranking ID does not exist, THEN the backend returns `404 Not Found` with error code `RANKING_NOT_FOUND`.

4. WHEN `name` is missing or empty, THEN the backend returns `400 Bad Request` with error code `VALIDATION_ERROR`.

5. WHEN `X-User-Id` is missing, THEN the backend returns `400 Bad Request` with error code `MISSING_USER_ID`.

6. WHEN an image is provided, THEN the backend processes it according to REQ-13 (image processing).

### REQ-10: List Items in a Ranking

**User Story:**
As a user, I want to see all items in a ranking with their scores, so that I can compare them.

**Traces:** A4, A11, A15, A19, A47, A50

#### Acceptance Criteria

1. GIVEN a valid ranking ID, WHEN the user sends `GET /api/v1/rankings/{rankingId}/items`, THEN the backend returns all items in the ranking with aggregated average scores (all users) per attribute and the calculated `overall` score.

2. WHEN the query parameter `mode=user` is provided along with a valid `X-User-Id` header, THEN the backend returns the caller's individual scores per attribute and the calculated `overall` based on their scores only.

3. WHEN `mode=user` is provided but `X-User-Id` is missing, THEN the backend returns `400 Bad Request` with error code `MISSING_USER_ID`.

4. WHEN `mode=user` is provided and the user has not rated an item, THEN that item's scores are returned as `null` for all attributes and `overall`.

5. WHEN the `sort` parameter is provided (e.g., `sort=-overall`, `sort=name`, `sort=-attributeName`), THEN the backend sorts items accordingly.

6. WHEN `sort` references an invalid field, THEN the backend returns `400 Bad Request` with error code `INVALID_SORT_FIELD`.

7. WHEN the ranking ID does not exist, THEN the backend returns `404 Not Found` with error code `RANKING_NOT_FOUND`.

8. THEN each item includes: id, name, imageUrl (pre-signed URL or null), scores object, overall, createdBy, createdAt.

### REQ-11: Update Item

**User Story:**
As the ranking creator or item creator, I want to update an item's name or image, so that I can correct mistakes.

**Traces:** A31, A33, A46, A51

#### Acceptance Criteria

1. GIVEN a valid `X-User-Id` that matches either the ranking's `ownerUserId` or the item's `createdBy`, WHEN the user sends `PUT /api/v1/rankings/{rankingId}/items/{itemId}` with updated fields, THEN the backend updates the item and returns `200 OK` with the updated item object.

2. WHEN `X-User-Id` does not match the ranking owner or the item creator, THEN the backend returns `403 Forbidden` with error code `NOT_AUTHORIZED`.

3. WHEN the item ID does not exist within the ranking, THEN the backend returns `404 Not Found` with error code `ITEM_NOT_FOUND`.

4. WHEN a new image is provided, THEN the backend processes it according to REQ-13 and replaces the previous image in S3.

5. WHEN `X-User-Id` is missing, THEN the backend returns `400 Bad Request` with error code `MISSING_USER_ID`.

### REQ-12: Delete Item

**User Story:**
As the ranking creator or item creator, I want to delete an item, so that I can remove irrelevant entries.

**Traces:** A27, A31, A46, A51

#### Acceptance Criteria

1. GIVEN a valid `X-User-Id` that matches either the ranking's `ownerUserId` or the item's `createdBy`, WHEN the user sends `DELETE /api/v1/rankings/{rankingId}/items/{itemId}`, THEN the backend deletes the item, its associated ratings, and its S3 images, and returns `204 No Content`.

2. WHEN `X-User-Id` does not match the ranking owner or the item creator, THEN the backend returns `403 Forbidden` with error code `NOT_AUTHORIZED`.

3. WHEN the item ID does not exist within the ranking, THEN the backend returns `404 Not Found` with error code `ITEM_NOT_FOUND`.

4. WHEN `X-User-Id` is missing, THEN the backend returns `400 Bad Request` with error code `MISSING_USER_ID`.

### REQ-13: Image Processing and Storage

**User Story:**
As a user, I want to attach an image to an item (via upload or URL), so that the ranking table displays a visual representation of each item.

**Traces:** A5, A34, A35, A36, A37

#### Acceptance Criteria

1. WHEN the user provides an image via **file upload** (multipart/form-data), THEN the backend validates the file format (JPEG, PNG, or WebP only) and size (max 10 MB).

2. WHEN the user provides an **image URL** (`imageUrl` field), THEN the backend downloads the image from that URL, validates format and size.

3. WHEN the image is valid, THEN the backend:
   - Optimizes the original to max 800×800px, WebP format, quality 80.
   - Generates a thumbnail at 150×150px, WebP format, quality 75.
   - Stores both versions in S3 under the item's path.

4. WHEN the image format is not JPEG, PNG, or WebP, THEN the backend returns `400 Bad Request` with error code `INVALID_IMAGE_FORMAT`.

5. WHEN the image exceeds 10 MB, THEN the backend returns `400 Bad Request` with error code `IMAGE_TOO_LARGE`.

6. WHEN the image URL is unreachable or returns an error, THEN the backend returns `400 Bad Request` with error code `IMAGE_DOWNLOAD_FAILED`.

7. WHEN the frontend requests an item's image, THEN the backend generates a **pre-signed URL** (valid for 1 hour) for the optimized image and thumbnail, and includes them in the item response.

8. THEN S3 objects are never publicly accessible. All access is via pre-signed URLs only.

### REQ-14: Submit or Update Ratings

**User Story:**
As a user, I want to rate an item by providing scores for all attributes, so that my evaluation contributes to the ranking.

**Traces:** A4, A9, A10, A12, A38, A39, A46

#### Acceptance Criteria

1. GIVEN a valid `X-User-Id` header, a valid ranking ID, and a valid item ID, WHEN the user sends `PUT /api/v1/rankings/{rankingId}/items/{itemId}/ratings` with a `scores` object containing a score (integer 0–100) for **every active attribute** in the ranking, THEN the backend saves (or updates) the rating and returns `200 OK` with the saved rating object.

2. WHEN the `scores` object is missing scores for one or more active attributes, THEN the backend returns `400 Bad Request` with error code `INCOMPLETE_RATINGS` — partial ratings are never persisted.

3. WHEN any score value is not an integer or is outside the range 0–100, THEN the backend returns `400 Bad Request` with error code `VALIDATION_ERROR`.

4. WHEN the user has previously rated this item, THEN the backend **overwrites** the existing rating with the new scores.

5. WHEN the ranking ID or item ID does not exist, THEN the backend returns `404 Not Found` with the appropriate error code.

6. WHEN `X-User-Id` is missing, THEN the backend returns `400 Bad Request` with error code `MISSING_USER_ID`.

### REQ-16: Health Check

**User Story:**
As an operator, I want a health check endpoint, so that I can monitor the backend's availability and connectivity.

**Traces:** A53

#### Acceptance Criteria

1. WHEN any client sends `GET /api/v1/health`, THEN the backend returns `200 OK` with a JSON body containing `status` ("ok" or "degraded"), `version` (application version), `environment` (e.g., "local", "dev", "prod"), and `dynamodb` connectivity status ("connected" or "error").

2. WHEN DynamoDB is unreachable, THEN the backend returns `200 OK` with `status: "degraded"` and `dynamodb: "error"`.

3. THEN no `X-User-Id` header is required for this endpoint.

### REQ-17: Structured Error Responses

**User Story:**
As a frontend developer, I want consistent and structured error responses, so that I can handle errors programmatically.

**Traces:** A48

#### Acceptance Criteria

1. WHEN any request results in an error, THEN the backend returns a JSON body with the structure: `{ "error": { "code": "<ERROR_CODE>", "message": "<human-readable description>", "status": <HTTP status code> } }`.

2. THEN the HTTP status code in the response header matches the `status` field in the error body.

3. THEN error codes are uppercase, underscore-separated constants (e.g., `RANKING_NOT_FOUND`, `VALIDATION_ERROR`, `MISSING_USER_ID`, `NOT_OWNER`, `NOT_AUTHORIZED`).

4. WHEN an unexpected internal error occurs, THEN the backend returns `500 Internal Server Error` with error code `INTERNAL_ERROR` and a generic message (no stack traces or internal details exposed).

### REQ-18: Cursor-Based Pagination

**User Story:**
As a frontend developer, I want cursor-based pagination on list endpoints, so that I can efficiently navigate large result sets.

**Traces:** A43, A44

#### Acceptance Criteria

1. THEN all list endpoints (`GET /api/v1/rankings`, `GET /api/v1/rankings/mine`, `GET /api/v1/rankings/search`) support `limit` (default 20, max 50) and `cursor` (opaque string) query parameters.

2. WHEN `limit` exceeds 50, THEN the backend clamps it to 50 without returning an error.

3. WHEN `limit` is less than 1, THEN the backend returns `400 Bad Request` with error code `VALIDATION_ERROR`.

4. THEN the response includes a `pagination` object with `nextCursor` (string or null) and `hasMore` (boolean).

5. WHEN there are no more results, THEN `nextCursor` is `null` and `hasMore` is `false`.

6. WHEN an invalid cursor is provided, THEN the backend returns `400 Bad Request` with error code `INVALID_CURSOR`.

### REQ-19: Sorting (JSON:API Convention)

**User Story:**
As a user, I want to sort results by different fields, so that I can view data in the order most useful to me.

**Traces:** A15, A49, A50

#### Acceptance Criteria

1. THEN all list endpoints support a `sort` query parameter following JSON:API convention: ascending by default, `-` prefix for descending, comma-separated for multiple fields.

2. THEN the rankings listing endpoint supports sortable fields: `name`, `createdAt`, `updatedAt`.

3. THEN the items listing endpoint supports sortable fields: `name`, `overall`, and each individual attribute name (dynamically resolved per ranking).

4. WHEN `sort` is not provided, THEN the default sort is `-createdAt` (newest first) for rankings and `-overall` (highest first) for items.

5. WHEN `sort` references an unsupported field, THEN the backend returns `400 Bad Request` with error code `INVALID_SORT_FIELD`.

6. THEN the backend parses the `sort` parameter by splitting on `,`, stripping `-`/`+` prefixes, and validating each field name.

### REQ-21: Input Validation

**User Story:**
As a backend developer, I want all inputs validated at the API boundary, so that invalid data never reaches the domain layer.

**Traces:** A28, A30, A33, A39

#### Acceptance Criteria

1. THEN every endpoint validates all required fields, field lengths, and value ranges before processing.

2. THEN validation errors return `400 Bad Request` with error code `VALIDATION_ERROR` and a `message` describing which field(s) failed.

3. THEN the following field constraints are enforced:
   - Ranking name: 1–100 characters
   - Ranking description: 0–500 characters
   - Tags: 0–10 items per ranking
   - Attributes: 1–6 per ranking; name 1–50 chars, description 0–200 chars
   - Item name: 1–100 characters
   - Rating scores: integer 0–100
   - Image: JPEG/PNG/WebP, max 10 MB

4. THEN UUID fields (ranking ID, item ID, X-User-Id) are validated as proper UUID format.

### REQ-22: X-User-Id Header Handling

**User Story:**
As a backend developer, I want a consistent middleware for handling the `X-User-Id` header, so that user identity is resolved uniformly across all endpoints.

**Traces:** A3, A46

#### Acceptance Criteria

1. THEN a middleware extracts the `X-User-Id` header from every request and makes it available to handlers.

2. THEN for **write endpoints** (POST, PUT, DELETE) and user-scoped read endpoints (`/rankings/mine`, `/ratings/mine`), the middleware returns `400 Bad Request` with error code `MISSING_USER_ID` if the header is missing or not a valid UUID v7.

3. THEN for **public read endpoints** (GET rankings, GET items, search, recent, health), the header is optional. If present and valid, it is used to enrich the response (e.g., `isOwner` flag). If absent, the request proceeds anonymously.

4. THEN the backend never modifies, generates, or stores the User ID — it is treated as an opaque, client-provided identity.

| Error Code | HTTP Status | Description |
|---|---|---|

| `MISSING_USER_ID` | 400 | `X-User-Id` header missing or invalid on a required endpoint |
| `INVALID_SORT_FIELD` | 400 | `sort` parameter references an unsupported field |
| `INVALID_CURSOR` | 400 | Pagination cursor is malformed or expired |
| `INCOMPLETE_RATINGS` | 400 | Rating submission missing scores for one or more attributes |
